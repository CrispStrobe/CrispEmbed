# OCR backend and graph matrix

This is an implementation claim matrix, not a claim that every model artifact
is currently cached. “Full graph” means the inference-critical forward is
constructed as ggml graphs and dispatched through the selected backend. A GPU
build alone does not promote a CPU implementation.

**Reading rule.** Every cell cites either (a) an environment gate or code path
you can read today, or (b) a measurement with the date it was taken. A claim
with neither is marked `UNVERIFIED` plus the date it was last asserted — it is
never silently deleted, and a negative measurement is quoted as the negative.
Whole matrix re-verified against `src/` and `examples/cli/main.cpp` on
**2026-08-04**.

**Reachability.** All 18 orchestrator engines in `src/ocr_orchestrator.h`
(`enum class engine`) have a C-ABI id (`map_engine`, `src/crispembed.cpp`) and a
`--ocr-engine` name (`eng_id`, `examples/cli/main.cpp`) as of 2026-08-04;
`tests/test_cli_engine_names.py` fails if that ever regresses. No row below
claims an unreachable lane.

The default local diagnostic build used for CPU parity has `GGML_METAL=OFF`
and `GGML_CUDA=OFF`. A separate macOS build with `GGML_METAL=ON` passed the
`test-backend-smoke` backend graph smoke on Apple M1 as of 2026-07-31, both in
auto mode (`MTL0`) and with an explicit `test-backend-smoke metal` request; that
result has not been re-taken since. It validates backend/device selection only;
it does not promote any OCR row to “Full graph” without an engine-specific
residency and parity test. Explicit requests fail when the requested GPU is
unavailable instead of silently passing on CPU. CUDA has never been smoked on
this hardware — it is `UNVERIFIED` as of 2026-08-04, not “supported”.

Before trusting a `Metal/CUDA today` cell, check the build you are actually
running: a `build/` directory can sit at `GGML_METAL=OFF` for days unnoticed.
Read `CMakeCache.txt` and the `MTL0` line on stderr, and A/B only same-binary
runs.
